# 認証

## 1. 目的・概要

メールアドレスとパスワードでアカウントを作成し、ログインして利用する。認証済みユーザーだけがレシピ投稿・フォロー・お気に入り・感想などの操作を行える。

- トークンは **アクセストークン（短命）＋ リフレッシュトークン（長命・ローテーション方式）** の 2 本立て。
- ログイン画面の **「ログインを保持」** チェックで、リフレッシュトークンを端末に永続保存するか決める。
- **パスワードリセット**は「秘密の質問（質問文もユーザーが自由入力）＋ 答え」で本人確認する（メール送信は使わない）。

## 2. 画面・UI

関連画面: [ログイン](../screens/login.md) / [サインアップ](../screens/signup.md) / [パスワードリセット](../screens/password-reset.md) / [スプラッシュ](../screens/splash.md)。

### ログイン画面

- メールアドレス入力
- パスワード入力（**表示トグルボタンを併設**）
- **「ログインを保持」チェックボックス**
- ログインボタン
- 「パスワードをお忘れの方」リンク → パスワードリセット画面
- 「新規登録」リンク
- エラー表示: 認証失敗時「メールアドレスまたはパスワードが違います」

### サインアップ画面

- メールアドレス入力
- パスワード入力（表示トグル）
- パスワード確認入力（表示トグル）
- 表示名入力
- **秘密の質問**: 質問文（自由入力）＋ 答え
- 登録ボタン
- 「ログイン」リンク

> グローバル CLAUDE.md「ログイン機能の標準UI要件」準拠: パスワード欄には表示トグル、サインアップ・パスワードリセットには確認入力欄を設け、不一致時はクライアント側でエラー表示し API 呼び出しをブロックする。ログイン画面に確認欄は不要。

### パスワードリセット画面（認証不要）

1. メールアドレス入力 → 送信
2. 登録済みの**質問文を表示**
3. 同じ画面で答え + 新しいパスワード + 確認入力（表示トグル・一致チェック）をまとめて入力 → 1 回で送信
4. `POST /auth/password-reset/confirm` の成功後、ログイン画面へ
- 答え不一致・試行回数超過はエラー表示（[../non-functional.md](../non-functional.md) の試行回数ロック）

### ログアウト

- [マイページ](../screens/my-page.md)の「ログアウト」。`POST /auth/logout` でリフレッシュトークンを失効し、端末のトークンを破棄してログイン画面へ。

## 3. 振る舞い・ルール

### トークン

- メールアドレスは全ユーザーで一意。パスワードは Argon2id（`argon2-cffi`）でハッシュ化して保存。
- ログイン成功で **アクセストークン（例: 15 分）** ＋ **リフレッシュトークン（例: 30〜90 日）** を発行。
- アクセストークンは JWT とし、クレームに subject（ユーザー ID）と発行時点の `users.token_version` を含める。
- 認証依存性（FastAPI の `Depends`）は各リクエストで、subject のユーザーが存在すること、退会中でないこと、かつトークンの `token_version` が `users.token_version` と一致することを確認する。いずれかを満たさない場合は 401 を返す。
- パスワードリセット成功時は `users.token_version` を原子的に `+1` する。アカウント削除時も削除前に `+1` することを明示し、将来の全端末ログアウトでも `+1` する。これにより、それ以前に発行されたアクセストークンは有効期限内でも以降 401 になる。
- アクセストークン期限切れ時、クライアントは `POST /auth/refresh` にリフレッシュトークンを送り、**新しいアクセストークン ＋ 新しいリフレッシュトークン**を受け取る。
- クライアントはリフレッシュを **single-flight** で行い、同時に複数のリクエストで更新が必要になっても `POST /auth/refresh` は 1 本だけ実行し、他のリクエストはその結果を待つ。これにより、同一リフレッシュトークンの並行リフレッシュは発生しない。
- **ローテーション**: 使用済みリフレッシュトークンは即座に無効化。クライアントは保存中のリフレッシュトークンを新しいものへ差し替える。
- サーバーは、消費済み（無効化済み）のリフレッシュトークンが再提示された場合、例外なくリユースとみなし、そのトークンチェーン全体を失効させて再ログインを要求する（**例外**: チェーン内の全トークンが期限切れから 30 日（`REFRESH_TOKEN_EXPIRED_RETENTION_DAYS`）を過ぎると、定期ジョブがそのチェーンの行を物理削除する。その後に再提示されたトークンは「見つからない」として単に 401 になる。失効させるべき生きたトークンはもうチェーンに残っていないので、結果（401・再ログイン）は同じ。Issue #72 で決定）。猶予時間・リプレイレコード・同一応答の再返却は設けない。
- まれにネットワーク障害でリフレッシュ応答を取りこぼした場合は、再ログインを必要とする許容可能な稀ケースとして扱う。これが問題になる場合は、将来、リクエストにバインドした冪等キー（クライアント生成の nonce）方式の導入を検討する（→ [../todo.md](../todo.md)）。
- リフレッシュトークン本体はサーバー側でハッシュ保存・失効管理する（`refresh_tokens` テーブル）。
- `/auth/refresh` は「旧トークンの失効」＋「新トークンの発行」を**単一トランザクション**で行う。リユース検知時は同一トランザクションで `chain_id` 全体を失効させる。期限切れトークンの物理削除は定期バッチ（[../processing-model.md](../processing-model.md) §6・§8）。

### 「ログインを保持」

Webブラウザでは、refresh tokenをlocalStorageへ保存せず、HttpOnly Cookie
（`recipi_refresh_token`）で保持する。Cookieは `SameSite=Lax`、本番では
`Secure` を付け、`Path=/api/v1/auth` に限定する。WebのrefreshはCookieを自動送信し、
JavaScriptからrefresh token本体を読み取らない。Android / Tauriは従来どおり
Bearer tokenと各プラットフォームのセキュアストレージを使う。

Cookie認証を使うWebの状態変更リクエストは、許可Originを限定し、CORSの
`allow_credentials`を有効にする。CSRF対策としてSameSite属性とOrigin検証を併用する。

Tauriの開発時はExpo dev serverと同じ `http://localhost:8081` Originになるため、
通常ブラウザと区別するクライアント印を付けて、CookieではなくStronghold保存用の
refresh tokenをJSON応答で受け取る。この印は開発・テスト環境だけで有効にし、本番の
ブラウザにrefresh tokenを露出させない。

| チェック | 挙動 |
| --- | --- |
| ON | リフレッシュトークンを端末のセキュアストレージ（Android Keystore）に**永続保存**。アプリ再起動時、保存済みリフレッシュトークンで自動的にアクセストークンを再取得（自動再ログイン） |
| OFF | リフレッシュトークンを永続化しない（メモリ / セッションのみ）。アプリ再起動後は再ログインが必要 |

- 永続保存とローテーションは両立する（保存＝置き場所、ローテーション＝値の入れ替え）。ON でも更新のたびに保存値を差し替える。

### パスワードリセット

- サインアップ時に「秘密の質問（質問文）」と「答え」を登録。答えは**ハッシュ化して保存**（`security_answer_hash`）。質問文は平文（`security_question`）。
- リセットは `POST /auth/password-reset/request`（メール → 質問文）で質問文を表示した後、同じ画面で答え + 新パスワード + 確認入力をまとめて受け付け、`POST /auth/password-reset/confirm`（メール + 答え + 新パスワード）の 1 回の送信で本人確認と更新を完了する。答えだけを検証する中間エンドポイントは設けない。確認入力が新パスワードと一致しない場合はクライアント側でエラー表示し、API を呼ばない。
- 答えの比較は正規化して行う（前後空白除去・大文字小文字・全半角。具体仕様は → [../todo.md](../todo.md)）。
- 試行回数ロック・レート制限を設ける（[../non-functional.md](../non-functional.md)）。
- 当面の秘密の質問方式では、`request` 応答で登録済みユーザー固有の質問文を返すため、未登録メールかどうかの実在判別は避けられない。未登録メールを完全に秘匿するのは、将来メールベースのリセットを導入する時点とする。
- 緩和策として、未登録メールにも一定のダミー質問文を決定的に返すデコイ方式（メールのハッシュから固定候補集合を選ぶ）を検討する（→ [../todo.md](../todo.md)）。
- `confirm` は、未登録メール・答え不一致・新パスワード規則違反をすべて同じ 400 で返し、理由を区別しない。

## 5. API

### POST `/auth/signup`（認証不要）

```json
// request
{
  "email": "testuser_001@example.com", "password": "TestPass123!",
  "displayName": "テスト太郎",
  "securityQuestion": "はじめて飼ったペットの名前は？", "securityAnswer": "ぽち"
}
// response 201
{ "user": { "id": "…", "displayName": "テスト太郎" }, "accessToken": "…", "refreshToken": "…" }
```

- 409: メール重複

### POST `/auth/login`（認証不要）

```json
// request
{ "email": "testuser_001@example.com", "password": "TestPass123!", "rememberMe": true }
// response 200
{ "user": { "id": "…", "displayName": "テスト太郎" }, "accessToken": "…", "refreshToken": "…" }
```

- `rememberMe` はクライアントの保存挙動を決める情報（サーバーはリフレッシュトークンの有効期限判断などに利用してもよい）。
- 401: メール未登録 / パスワード不一致
- 409 `ACCOUNT_DEACTIVATED`: 認証情報が正しいが退会中。トークンは発行せず、クライアントは確認後に再開 API を呼ぶ。

### POST `/auth/reactivate`（認証不要）

```json
// request
{ "email": "testuser_001@example.com", "password": "TestPass123!", "rememberMe": true }
// response 200（通常ログインと同じ）
{ "user": { "id": "…", "displayName": "テスト太郎" }, "accessToken": "…", "refreshToken": "…" }
```

- 退会中アカウントだけを `deleted_at = NULL` に戻して再開する。プロフィール・アバター・レシピは復帰するが、退会時に消したフォロー・お気に入り・感想・通知・閲覧履歴は復帰しない。
- 401: メール未登録 / パスワード不一致 / 退会中でないアカウント。

### POST `/auth/refresh`（認証不要、リフレッシュトークンを body で送る）

```json
// request
{ "refreshToken": "…" }
// response 200
{ "accessToken": "…", "refreshToken": "…(新しい値)" }
```

- 401: 無効 / 期限切れ / 失効済み。リユース検知時はチェーン全体を失効。

### GET `/auth/me`（認証必要）

```json
// response 200
{ "id": "…", "displayName": "テスト太郎", "avatarUrl": null }
```

- 有効なアクセストークンに紐づく現在ユーザーを返す。Web クライアントは Cookie を使った `/auth/refresh` の成功後にこの API を呼び、画面表示に必要なユーザー情報を復元する。
- 401: Authorization ヘッダーなし / 無効・失効したアクセストークン / 退会済みアカウント。

### POST `/auth/logout`（認証必要）

```json
{ "refreshToken": "…" }
```

- 204。該当リフレッシュトークン（チェーン）を失効。

### POST `/auth/password-reset/request`（認証不要）

```json
// request
{ "email": "testuser_001@example.com" }
// response 200
{ "securityQuestion": "はじめて飼ったペットの名前は？" }
```

- 登録済みメールには登録された質問文を返す。当面は未登録メールに実在する質問文を返せないため、応答の違いによるアカウントの実在判別を許容する既知の制約とする。完全なユーザー存在秘匿は将来のメールベースのリセット導入時に行う。
- 未登録メールに決定的なダミー質問文を返すデコイ方式は未確定（→ [../todo.md](../todo.md)）。

### POST `/auth/password-reset/confirm`（認証不要）

```json
// request
{ "email": "testuser_001@example.com", "securityAnswer": "ぽち", "newPassword": "NewPass456!" }
// response 204
```

- 成功時は、204 を返す前に `users.token_version` を原子的に `+1` し、そのアカウントの全リフレッシュトークン（全チェーン）を失効させる。リセット前に発行されたアクセストークンは、以降のリクエストで `token_version` が一致しないため 401 になる。
- 400: 未登録メール / 答え不一致 / 新パスワード規則違反（いずれも同じエラーで理由を区別しない）
- 429: 試行回数超過

## 7. 受け入れ基準

- [ ] 未登録メールで登録でき、同じメールの重複登録は 409 で拒否される
- [ ] サインアップで秘密の質問・答えが未入力だと 400
- [ ] サインアップでパスワードと確認が不一致だと、クライアントでエラー表示し API を呼ばない
- [ ] 誤ったパスワードでのログインは 401 になる
- [ ] 退会済みアカウントの正しいログインは 409 となり、確認後に再開できる
- [ ] アクセストークン期限切れ後、`/auth/refresh` で新トークンペアを取得でき、古いリフレッシュトークンは使えなくなる
- [ ] 無効化済みリフレッシュトークンを再提示すると、例外なくチェーン全体が失効して再ログインが要求される（チェーンの全トークンが期限切れから 30 日を過ぎて行が削除された後は、単に 401 で再ログインが要求される）
- [ ] クライアントが single-flight でリフレッシュするため、正規利用で不要なログアウトが起きない
- [ ] 「ログインを保持」ON でアプリを再起動すると自動的にログイン状態が復帰する
- [ ] Webではrefresh tokenをlocalStorageへ保存せず、HttpOnly CookieでF5後のセッションを復元する
- [ ] 「ログインを保持」OFF でアプリを再起動すると再ログインが必要
- [ ] パスワードリセットで、正しい答えを入力すると新パスワードを設定でき、以後それでログインできる
- [ ] パスワードリセット後、リセット前に発行された既存のリフレッシュトークンは使えなくなる
- [ ] パスワードリセット後、リセット前に発行された既存のアクセストークンでリクエストすると 401 になる
- [ ] 答えを一定回数間違えると一時的にロックされる
- [ ] パスワードは平文で DB に保存されていない（秘密の答えも同様）
- [ ] ログアウト後はリフレッシュトークンが失効し、自動再ログインできない

- 秘密の質問方式では登録済みメールの完全な秘匿は行わず、完全な秘匿は将来のメールベースのリセット導入時とする。緩和策のデコイ方式（メールのハッシュから固定候補集合のダミー質問文を決定的に選ぶ）の採否 → [../todo.md](../todo.md)
- リフレッシュトークンの具体的な有効期限（保持 ON / OFF で変える場合の値）→ [../todo.md](../todo.md)
- 秘密の質問・答えの後からの変更手段は**確定**: **マイページ →「アカウント設定」画面**で変更する（Issue #240・#242）。プロフィール編集（他人への見せ方）とは分け、現在のパスワードで再認証してから認証情報を変える操作をこの画面にまとめる。`PUT /users/me/security-question`。現在のパスワード欄は表示トグル付き、新しい答えは伏せて入力し確認欄と一致しなければ送らない。パスワード違いは 403 `REAUTH_FAILED`（401 にしない。ログアウトさせないため）
- 将来、プロフィール側にパスワード変更機能を追加する場合も、変更成功時にそのアカウントの全リフレッシュトークンを失効させる。
- メールアドレス変更は**実装済み**（Issue #241）。`PUT /users/me/email`
  - **再確認メールは送らない**。このプロジェクトはメール送信基盤を持たない（パスワードリセットが秘密の質問方式なのと同じ理由。§3「パスワードリセット」）。代わりに**現在のパスワードによる再認証**と、クライアント側の**確認用再入力欄**で打ち間違いを防ぐ
  - 再認証の失敗は **403 `REAUTH_FAILED`**（401 にしない。401 だとクライアントが「トークン切れ」と解釈してリフレッシュ → 再送 → セッション破棄まで進み、打ち間違いだけでログアウトさせられる）
  - 既に使われているアドレスは **409**。**退会済みのアカウントが持つアドレスでも同じ 409** にする（区別すると退会の事実が漏れる。退会は論理削除なので `/auth/reactivate` で再開しうる）
  - 成功すると**既存のセッションを全て失効**させ、呼び出し元用に新しいトークン対を発行して返す。`token_version` を上げるだけでは足りない（`/auth/refresh` は世代を見ないので、他端末はリフレッシュで復帰できてしまう）
  - `rememberMe` は**必須**。新しいリフレッシュトークンの有効期限を決めるため。既定値を置くと、保持 OFF の利用者が黙って長期セッションに切り替わる
  - **再試行は冪等ではない**。応答だけ失われた場合、手元のトークンは既に失効しているので、新しいアドレスでのログインが必要になる
  - **Web で「保持しない」を選んでいた場合、意図せず長期 Cookie に切り替わらない**（修正済み。Issue #275）。Web の Cookie は中身が JS から見えないため、以前は再読み込み後の復元時に `rememberMe: true` を無条件に設定しており、保持 OFF の利用者がメール変更等をすると長期 Cookie になってしまっていた。ログイン・登録・再開・メール変更の時点の選択を `localStorage`（トークンではない）に控え、復元時に読む方式にした（控えが無ければ `false`）
  - **応答が届かない・端末への保存に失敗した場合の案内**（修正済み。Issue #276）。成功時にサーバー側で全セッションを失効させる特性上、これらのケースでは**サーバー側だけ変更が完了している**。一律「通信エラー。もう一度お試しください」ではなく、「変更されている可能性があるため、もう一度送信せず新しいメールアドレスでログインし直してください」を案内し、自動では再送しない
