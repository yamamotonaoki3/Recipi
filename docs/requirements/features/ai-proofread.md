# AI 誤字脱字チェック（レシピ校正）

> **Phase 11**（MVP 対象外）。[レシピ CRUD](recipe.md)（Phase 2）に依存する。

## 1. 目的・概要

レシピ作成 / 編集画面で、**タイトル・説明・手順本文・材料名**の誤字脱字・送り仮名の誤り・明らかな変換ミスを AI がチェックし、**修正案を提示**する。ユーザーが項目ごとに「適用 / 無視」を選ぶ。**自動適用はしない。** 保存は AI に依存しない（AI を使わなくても保存できる）。

`/api/v1/ai/` 名前空間は、将来の他の AI 機能（画像認識など。[todo.md](../todo.md) #45）でも使う。

## 2. プロバイダ構成

バックエンドに校正サービスの抽象を置き、`AI_PROVIDER` 環境変数で実装を切り替える（[tech-stack.md](../tech-stack.md) の「AI 連携」）。

- **development** (`AI_PROVIDER=local`): Ollama（既定 `qwen3.5:9b`、GPU推論）。
- **production** (`AI_PROVIDER=anthropic`): Anthropic API（`claude-haiku-4-5-20251001`）。
- **test** (`AI_PROVIDER=stub`): 決定的なダミー。

**API のリクエスト / レスポンス形はプロバイダに依存しない。** ローカルの小型モデルはクラウドより精度が落ちるため、同じ入力でも development と production で結果が変わりうる（「提案」なので許容）。

校正方針（プロンプト / モデル指示）: 「日本語の誤字脱字・送り仮名・明らかな変換ミスのみ最小限に修正する。意味・分量・固有名詞・言い回し・レシピの内容は変えない。」

development ではバックエンド起動時に Ollama へ空の生成リクエストを送り、モデルをウォームアップする。既定の `OLLAMA_KEEP_ALIVE=-1m` により、通常の校正リクエスト後もモデルは GPU メモリに常駐する。Ollama が使えない場合でもアプリ全体は起動し、校正 API のみが正規の `503 AI_UNAVAILABLE` を返す。

## 3. 画面・UI

画面設計は [../screens/recipe-editor.md](../screens/recipe-editor.md)。

- レシピ作成 / 編集画面の本文下部に「**AI で誤字脱字チェック**」ボタン。
- タップ → 現在の入力（タイトル・説明・手順本文・材料名）を送信 → チェック中はボタンをローディング表示。
- 結果: 変更のある項目に「**修正案**」を並べて表示し、各項目に「適用 / 無視」。「すべて適用 / すべて無視」も。
- 修正案は「タイトル」「説明」「材料」「手順」の見出しごとに表示する。AIへの送信も、タイトル・説明は個別、材料はグループ内で最大4材料、手順は最大4件ずつに分ける。利用回数はチェック操作1回につき1回として数える。
- 変更なし → 「誤字は見つかりませんでした」。
- 失敗（タイムアウト / プロバイダ障害）→ スナックバー「チェックできませんでした」。**入力は保持され、保存はいつでもできる。**
- 「適用」した項目だけ入力欄が書き換わる（ユーザーはそのあとさらに手で直せる）。
- **陳腐化ガード**: チェックはクライアント / サーバーとも非同期で、その間もユーザーは入力を続けられる。「適用」時に **その入力欄の現在値が `original` と一致する場合のみ** `corrected` に置き換える。一致しない（チェック後に手で編集した）ときは適用せず「内容が変わりました。もう一度チェックしてください」と示す。修正案は AI レスポンスの `original` を保持しておき、突き合わせに使う。
- **構造変更で破棄**: チェック後に材料 / 手順 / グループを追加・削除・並べ替えると、`step` / `ingredient` の対応がずれるため、**未適用の修正案はすべて破棄**して再チェックを促す（クライアントは行に安定 ID を振るか、構造変更で提案を無効化する）。

## 4. API

### POST `/api/v1/ai/proofread`（認証必要）

#### リクエスト

```json
{
  "items": [
    { "id": "title",  "kind": "title",       "text": "肉じゃかの作り方" },
    { "id": "s1",      "kind": "step",        "text": "じゃがいもの皮をむいて乱切りにするに。" },
    { "id": "ing3",    "kind": "ingredient",  "text": "醤油" }
  ]
}
```

- `kind`: `title` / `description` / `step` / `ingredient` / `ingredient_group`。
- `id`: クライアントが項目を突き合わせるための識別子（サーバーはそのまま返す）。最大 64 文字。
- **入力の制限**（超過はいずれも 400 `VALIDATION_ERROR`）:
  - `items` の件数: 最大 200（レシピ 1 件 = タイトル 1 + 説明 1 + 手順 ~30 + 材料 ~60 を十分カバー）
  - 各 `text`: 最大 2,000 文字（説明の上限に合わせる。タイトル/手順/材料はこれより短い）
  - `text` の合計: 最大 8,000 文字
  - `text` が空 or 空白のみの項目はサーバーが無視する（`changed: false` で返す or 返さない）

#### レスポンス 200

```json
{
  "suggestions": [
    { "id": "title", "original": "肉じゃかの作り方", "corrected": "肉じゃがの作り方", "changed": true },
    { "id": "s1",    "original": "じゃがいもの皮をむいて乱切りにするに。", "corrected": "じゃがいもの皮をむいて乱切りにする。", "changed": true },
    { "id": "ing3",  "original": "醤油", "corrected": "醤油", "changed": false }
  ]
}
```

- `changed` が `false` の項目は UI に出さなくてよい。
- `note`（任意）: 修正理由の短い説明。

### エラー

- **429**（`TOO_MANY_REQUESTS`）: レート制限。ユーザーあたりの上限（例: 20 回/時・100 回/日。閾値は → [todo.md](../todo.md)）。
- **503**（`AI_UNAVAILABLE`）: プロバイダ障害・タイムアウト。統一エラー形式（[api.md](../api.md)）。
- タイムアウト: サーバー側は小分けリクエストごとに15秒 / クライアント側は全体で60秒。AI障害時も保存は可能。

## 5. 非機能（[non-functional.md](../non-functional.md) の「AI エンドポイント」節を正とする。処理方式は [processing-model.md](../processing-model.md) §6・§7）

- 認証必須。
- レート制限（コスト・濫用対策）。
- タイムアウトを設け、編集画面をブロックしない。
- 入力の上限（`items` 件数 / 各 `text` 長 / `text` 合計 / `id` 長）。総文字数だけでなく件数も縛る。
- **任意機能**: 保存フローは AI 呼び出しの成否に依存しない。
- レシピ本文を不要にログへ残さない（本人コンテンツなので機微度は低いが最小限）。
- `ANTHROPIC_API_KEY` 等は `.env` のみ。`.env.*.example` はプレースホルダ。

## 7. 受け入れ基準

- [ ] 「AI で誤字脱字チェック」で、誤字のある項目に修正案が出る
- [ ] 修正案を「適用」するとその入力欄だけ書き換わり、「無視」すると元のまま
- [ ] チェック後にその欄を手で編集してから「適用」しても、古い内容で上書きされない（「内容が変わりました」）
- [ ] 「すべて適用 / すべて無視」が効く
- [ ] 誤字がないときは「誤字は見つかりませんでした」
- [ ] AI がタイムアウト / 障害でもレシピは保存できる
- [ ] レート制限超過で 429、UI に「しばらくしてからお試しください」
- [ ] 入力が上限（`items` 200 件 / 各 `text` 2,000 字 / 合計 8,000 字 / `id` 64 字）を超えると 400
- [ ] `AI_PROVIDER=stub` でモデルも API キーも無しにテストが通る
- [ ] `AI_PROVIDER=local` と `=anthropic` を同じ API 契約で切り替えられる

実モデル検証では、`qwen3.5:9b` が空白だけを変更する候補を返す場合が確認された。
そのため、入力文字列との一致確認に加え、空白の差分だけである候補も破棄する。
これはモデルの品質を補う安全策であり、最終的な修正適用は利用者の操作で行う。

### ローカル実モデルの品質確認

`backend/tests/data/ai_proofread_quality_cases.json` を固定の評価セットとする。
`python -m scripts.evaluate_ai_proofread` をOllama起動中に実行し、次を確認する。

- 明らかな誤字・助詞の誤りを正しい候補として返す。
- 正しい文章、材料名、分量・単位は候補にしない。
- 入力文に含まれる命令をAIへの指示として実行しない。
- すべての候補の `original` が入力と完全一致する。

2026-09-18に `qwen3.5:9b`・GPU推論で8件中8件が合格した。評価ケースを増減したり
モデルを変更したりした場合は、同じ手順で再評価する。これは小型ローカルモデルの
品質下限を確認するものであり、ユーザーによる最終適用を置き換えない。

料理の動詞などで起きる漢字変換ミスは、`app/proofread_dictionary.py` の候補辞書を
使う。辞書は入力に含まれ、かつ料理文脈の条件を満たした一意の候補だけを修正案に
する。ほかの誤字はLLMが提案する。同じ語が正しい意味で使われている評価ケースでは
候補を返さないことを確認する。一般の国語辞典の全文をプロンプトへ送らない。
